Layout system · desktop density · 1440–1920px

Desktop is not a wide phone

design/mock-responsive.html (owner-approved, merged 5ef96ba) added the missing 768–1439px tablet tier and fixed the segmented-control and tag-wrap defects it found there. It left one line unexamined for every screen: "Desktop · ≥1440px (unchanged from the approved mock)." That line is the subject here. An independent reviewer, then STATUS.md's own "Known debt" entry (2026-08-22 round-2 tablet review), both measured the same thing: Pantry, Plan, Shopping, Recipe detail and Home each leave 40–80% of a 1512×950 or 1920×1080 viewport empty on a populated screen, because the desktop tier reflows width (via AppShell's .mainWide 1680px cap and .rgrid's auto-fill grid) but never reflows height — every list, card stack and calendar column is sized as if it were still on a 900px tablet, just centred in more air. This file is the missing pass: what desktop earns beyond 1440px, and what it still deliberately does not touch.

It extends mock-responsive.html; it does not replace it. Phone and the 768–1439px tablet tier are unchanged and are not repeated here — go there for those. The token layer (spacing, type scale, colour) is a parallel proposal from another agent; every value below is described by role ("a touch-target row", "a card-head label"), not by px or rem, so the two proposals can be reconciled without either one re-deciding the other's numbers.

The system

The reviewer's real charge isn't "desktop looks wrong" — it's that no rule decided what desktop should look like, so flexbox decided by default. Here is the rule, stated once, so every screen below is an application of it rather than a fresh judgement call.

Breakpoints — unchanged, restated

TierRangeInput modelWhat changes here
Phone0–767pxThumb, one-handedNothing — out of scope for this file
Tablet768–1439pxTouch, two-handed or proppedNothing new — mock-responsive.html owns this tier
Desktop1440–1919pxPointer, full peripheral visionThis file: vertical density + genuine multi-column content
Wide desktop≥1920pxPointer, external monitorThis file: same column counts as 1440–1919 — see below for why not more

1920px is not a new breakpoint with new rules — it's evidence for the existing 1680px cap on .mainWide. A 1920px browser window still hands content a 1680px column; the extra 240px is margin, and margin is the one thing UI_DESIGN.md §13 already says desktop should not be paid in ("width buys information, not padding"). Adding a fifth tier to grow columns further at 1920 would violate that rule, not honour it. The fix desktop needs is not "more columns as the window grows" — the auto-fill grids already do that correctly, up to the cap — it's "more rows visible per column," which is a height problem, not a width one.

The actual defect, traced

Four screens, one shape of bug. pantry.module.css's rail is a fixed 250–290px column (already correct — an earlier draft's 2fr proportional rail was fixed before this pass) beside a minmax(0,1fr) list — but the list itself is one column of 44–48px rows, so at 950px of viewport height it shows ~14 rows and stops, with everything below the fold blank. plan.module.css's .week is repeat(7,minmax(0,1fr)) — correct column count — over .day cells fixed at min-height:118px, so the calendar renders as a ~160px strip at the top of a 950px page no matter how tall the window is. shopping.module.css repeats the pantry shape: fixed rail, single list column, same shortfall. Recipe detail's .rphoto is capped at 320px (correct — see the photo section) but sits inside the same 840px reading measure as its ingredient list, so the photo and the two-line "serves 4 · 45 min" caption are the only things beside each other; nothing else on the page uses the second dimension of the space a photo rail implies. None of these need a new grid system — they need the existing grids given permission to use height, and in two cases (Plan, Recipe detail) a second column that does not exist yet.

Three rules that generalise across every screen below

RuleSays
A column earns a second columnonly when the second column answers a question the first one raises — "why is this on my list" (Shopping), "what else needs using soon" (Plan) — never as decoration. A screen with nothing to say in a second column stays one column at every tier. Recipe editor, Ingredient editor and Settings are forms; forms don't get wider, they get shorter reading lines (§ Left alone).
Vertical density is "does the fold matter."A screen is done at a width when, for a realistic populated household (the fixtures already in src/sheets/mocks, not an empty demo), the *first visible screenful* contains most of what a person came for — tonight's meal, the week ahead, the items about to expire — without the page reading as mostly background. Concretely: no list/grid may render with a fixed min-height that stops well short of its container's available height when there is more content to show.
Multi-column content stays list-first(UI_DESIGN.md §6). Turning Pantry's rows into two side-by-side columns of ListRows is still a list — same semantics, same component — just wrapped at a column boundary instead of only a viewport boundary. It is not the same move as switching to EntityTable, which stays reserved for screens with genuinely tabular columns (Price history, below).

Recipes

Reviewer's number: cards ending at x=751 in a 1480px column, ~51% used. Caveat, stated plainly: the live source I read (recipes.module.css:121) is already grid-template-columns:repeat(auto-fill,minmax(230px,1fr)) inside .mainWide's 1680px cap — a grid that reflows correctly by construction, and /recipes is already in WIDE_ROUTES. I could not reproduce the 51% figure by reading the CSS alone; it may predate the WP-PHOTO-era bump from 168px to 230px cards, or reflect a viewport this pass didn't check live. Recommend re-measuring live before writing any ticket against this screen — the design below assumes the grid already reflows, and focuses the real remaining gap: how many rows are visible without scrolling.

A recipe

Divergence from the current per-route decision, stated explicitly: today every recipe page lives inside AppShell.tsx's default .mainMeasure (840px), same as Settings and the editors. I'm proposing a fourth container mode — call it mainDetail, ~1080px — only for /recipes/:id. Reasoning: the photo (§ below) is a fixed 320px element that does not belong inside an 840px reading column stealing width from ingredient lines; it belongs beside them. 320px photo + 24px gap + an unchanged ~680px reading measure for ingredients/steps ≈ 1024px, so 1080 is the honest number, not 1680 — this is still a detail/reading screen, not a browse grid, and should not get WIDE_ROUTES's cap.

Desktop≥1440px

Photo + metadata card pinned left at a fixed 320px (identical size to tablet — the photo never grows past its stored resolution, see the photo section); ingredients and method keep their existing reading measure on the right. This is new width, not new content — nothing here is invented, the photo and the ingredient list both already exist, they were just stacked instead of paired.

Pantry

The clearest case of "the rail measured, the list didn't." pantry.module.css's rail is already a correct fixed width (250px, growing to 290px only at ≥1512 to hold three filter chips — not the proportional 2fr the reviewer describes, so that part of the original defect appears already fixed on this branch). The list beside it is one column of ~48px rows. At 950px of usable list height that's ~14 lots before scroll, in a household that easily has 30–50 active lots.

Desktop≥1440px

Each pantry-group section (Fridge, Freezer, Pantry) lays its lot rows into a 2-column card grid instead of one column — this is ListSection's existing grid prop (already used for the Ingredients catalog at tablet), extended to fire at desktop for Pantry specifically, not a new component. Row height is unchanged; only the column count changes, so ~14 rows becomes ~28 in the same vertical space. Rail stays fixed-width and unchanged.

Why 2 columns, not 3. A pantry row is name + quantity + freshness meter — at 3 columns inside a ~1170px list pane (1512 − 290px rail − gaps) each column is ~380px, comfortable; the reason to stop at 2 rather than push to 3 is that most households' individual pantry groups (Fridge, Freezer, Pantry) run 6–15 lots each, so 2 columns already clears most groups without scrolling, and a 3rd column mostly serves the rare 20+-lot Pantry-dry-goods group at the cost of a visibly thinner column everywhere else. This is a judgement call, not a measured constraint — worth revisiting once real household data volumes are known.

Plan

Not touching the tablet band. The 4-column Mon–Thu/Fri–Sun grid at 768–1439px is the approved mock, replaced a seven-column layout that measured unusable at that width, and a separate tablet review independently confirmed it — I have no new data that overturns that, so it stays exactly as shipped. This section is only about ≥1440px, where the app already renders the full seven-column week (plan.module.css:74, unaffected by the tablet decision) — and where .day's min-height:118px is the entire defect: seven correct columns, each one a ~160px-tall strip at the top of a 950px page.

Desktop1440–1679px

Day columns stretch to fill the available row height (align-items:stretch instead of a fixed min-height), so more of the week's slots become visible without opening a day — pinned staples, generated picks and leftover placements all show at once instead of only the first 1–2. No rail yet: seven stretched columns plus a 250px+ rail doesn't fit at 1440 without narrowing a day column below a legible width (7 × ~150px + rail ≈ 1300px content, workable; adding the ≥120px gap a rail needs pushes a day column under ~135px, where a slot's recipe name + servings stepper starts wrapping).

Second most debatable call in this proposal. A rail that appears only past 1680px is an unusual pattern — most of this system treats 1440–1919 as one tier. I chose it because the alternative (rail at all desktop widths) measurably breaks the seven-column week, which is the one thing UI_DESIGN.md §13 explicitly says "is the screen that justifies desktop" — I'd rather ship a rail that only sometimes appears than one that always appears and sometimes ruins the calendar. Shopping

Same shape as Pantry: fixed rail (already correct), single-column category list beside it. Shopping categories (produce, dairy, pantry staples, …) run short — typically 2–8 items — so a single column stacks 6–10 short category blocks vertically, most of which have visible whitespace under their last row before the next category header, while the two-thirds of the width left of the rail sits unused.

Desktop≥1440px

Category cards lay out 2-up in the list pane, ordered top-to-bottom-then-across (reading order, not aisle order — aisle order only matters in-store, i.e. on phone, which is untouched). This is the one screen where I considered and rejected a masonry/balanced-column layout: simple row-major 2-up keeps category order predictable, which matters more here than perfectly even column heights.

Home · Ingredients · editors · Scan · Price history · Settings

Not every screen needed a desktop pass. Here's the disposition of each, briefly, and why.

Home

Already correct. mock-responsive.html's desktop frame (two-column: day cards + freshness rail) matches the "second column earns its place" rule directly — no defect was reported here and none was found. Leaving it alone. One temptation resisted: adding a third widget in the freed space at 1920px ("recently cooked," "shopping preview"). Rejected — Home's job is "what's for dinner and what's about to spoil," and a third card competes with that rather than extending it.

Ingredients (catalog)

Explicitly not re-solved here — a separate agent owns the live regression where ListSection.module.css:28 scopes the tablet grid to 768–1439.98px and reverts to one column at 1440+. The one thing this pass adds: whatever fix lands there should extend the existing rule rather than add a new one — the grid should keep widening past 1439.98px inside the same mainWide 1680px cap the Recipes grid already uses, landing at a similar column count (5–6 at 1512px for a 230px-minmax card, per the Recipes math above), not stop at the tablet's 3.

Recipe editor, Ingredient editor, Settings

Stay single-column, capped at the reading measure, at every tier. These are forms — WP-VC4 already gave the recipe editor real per-step cards, which is the correct desktop enhancement for a form (shorter scroll, not more columns). A two-column form fights how people actually fill one in: field N+1 is either below or it's nowhere obvious. This is the clearest "screen that should stay one column" answer the brief asked for.

Scan (barcode)

Camera-first; desktop use is rare (no camera, or a webcam nobody points at a can). Leave centred and narrow. Widening a live camera viewport or a manual-entry fallback form buys nothing — there's no multi-column content here to reflow into.

Price history

The one screen that should adopt EntityTable (UI_DESIGN.md §6: "retained only where columns genuinely mean something") rather than a list — date, price, unit price and source are real independent columns, not a leading/trailing-slot row. Proposal: a chart across the full mainWide column at top, the EntityTable below it at the reading measure — the chart is the browse surface that earns width, the table is reference detail that doesn't need to be wider than it is legible.

The photo question

Verdict: agree the current desktop treatment undersells it; disagree that the fix is bigger. The right fix is a role, held constant, not a size increase.

The role already exists and is right — it just isn't being honoured. mock-responsive.html's own CSS comment states the rule precisely: photos are encoded at 512px / 32KB, and the display cap is the storage cap seen from the other end — nothing should ever render wider than that source, or it's an upscale of a photo the user already took, which reads as soft and cheap on any 2x display. Per-context caps are already defined: 80px leading card thumbnail, 320px 4:3 detail inset, 240px step image, 44–52px list glyph. The reviewer's complaint — "squeezed into a 290px sidebar, matched to an unrelated card's width" — is exactly what happens when a screen borrows some other column's width (Pantry's rail happens to be ~290px) instead of using the photo's own 320px token. That's not an undersized photo, it's a photo with no seat of its own.

The fix, applied above in Recipe detail: give the photo a fixed 320px column that is its own layout primitive, present at every tier ≥768px, never resized to match a neighbour. Held constant across tablet and desktop — not because desktop couldn't fit something bigger, but because bigger than 320 CSS px is already past the point of showing the real photo, on the one class of display (2x) most people actually have. I disagree with the premise that a meal planner's highest-value glance signal needs to be large to do its job — recognition ("yes, that's the roast chicken") needs less resolution than the reviewer's framing implies, and a consistent modest size across every screen is worth more than a hero treatment on one screen and a shrunk one everywhere else.

What this deliberately does not touch

Plan's tablet 4-column band

Explicitly out of scope per the brief — approved mock, independently reviewed, no new evidence against it. Desktop's 7-column week (≥1440px) is untouched in column count; only row height changes.

The 1680px cap on .mainWide

Kept exactly as is. The problem this file solves is vertical, and widening the cap further would only add more narrow columns on an ultrawide monitor — the opposite of the fix.

Forms (Recipe editor, Ingredient editor, Settings)

Stay single-column, capped at the reading measure, at every tier — see above.

The photo's maximum displayed size

320px held constant from tablet through 1920px+ — see the photo section. Resisting the temptation to let it grow just because desktop has the room.

Ingredients catalog's actual fix

Owned by another agent already in flight; this file states only the constraint it should converge on (§ Other screens).

Colour, spacing and type tokens

Owned by the parallel token-layer proposal. Every measurement above is stated as a role, not a value, for exactly that reason.

How we'd know it shipped

Three approved designs on this project reached the mock and never reached the code — photos, the Plan calendar, and the segmented-control wrap fix, the last one demoed at almost exactly the width that later broke in production (STATUS.md, "Known debt"). The lesson taken here: every claim above becomes an assertion on measured geometry, not a screenshot a reviewer eyeballs once.

AssertionHow
Recipes grid renders ≥6 columns at 1512pxPlaywright at 1512×950: read getComputedStyle(.rgrid).gridTemplateColumns, split on whitespace, assert length >= 6. Re-run at 1920×1080, same viewport-independent assertion — proves the 1680px cap is holding column count flat, not growing it.
Pantry lots lay out 2 columns at ≥1440px, 1 column at <1440pxBounding-rect diff: assert the x-position of the 2nd visible lot row differs from the 1st at 1512px (same row, second column) and equals it at 1024px (stacked).
Plan day columns fill available height, not a fixed 118pxAssert .day's rendered height at 1512×950 is within, say, 20px of the .week container's height — not a fixed constant — for a populated week fixture (not the empty-state one).
Shopping shows ≥2 category cards per row at ≥1440pxSame bounding-rect column check as Pantry, against a fixture with ≥4 categories.
Recipe photo is always exactly 320px, never resized to a neighbour's widthAssert .rphoto's computed width equals the shared token (not a magic number duplicated per screen) at 768, 1024, 1440 and 1920px — and assert it is not equal to the pantry rail's computed width, which is the literal bug being fixed.
The 230px-container SegmentedControl wrap fix (already in the mock, never shipped) A dedicated regression test: render SegmentedControl with 4 options in a 230px-wide parent, assert it lays out 2×2 (via row count from bounding rects) rather than overflowing — this is the specific case STATUS.md names as caught by review, not by process, twice already.
Dead-space gateFor each of Pantry/Plan/Shopping with a populated fixture at 1512×950: measure the distance from the bottom of rendered content to the viewport bottom; assert it's under some agreed threshold (proposal: 150px — roughly one more row's worth). This directly operationalises "40–80% empty below the fold" as a number that fails CI if it regresses, rather than waiting for the next screenshot review to notice.

All of these are assertable today with Playwright + getComputedStyle/ getBoundingClientRect against the existing E2E harness (TESTING.md's port table) — no new tooling. The point is process, not technology: geometry assertions land in the same PR as the layout change, so "approved but unshipped" stops being possible for this feature the way it was for photos, the calendar and the segmented control.
