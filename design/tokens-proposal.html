Feeder — token layer
Audit Type Color Spacing Migration Keep Fluid type Enforcement

Design proposal · not yet approved · no src/ changed

A token layer Feeder can actually point at

Nine font sizes across four screens that no reader can tell apart. A 184px bar that thinks it's 15% of a row. A colour system authored in three different spaces at once. None of this is a taste problem — it's an arithmetic problem, and it's fixable without touching what already works: the radius set and the AAA contrast are staying exactly as they are.

Awaiting owner sign-off before any src/ change lands

The root cause is one media query, not clamp(). src/index.css sets font: 18px/145% on :root, then flips to font-size: 16px under @media (max-width: 1024px). No clamp() exists anywhere in the shipped CSS — the fluid-looking cluster is every rem value in the app, doubled, because the multiplier that produces 15.3px on desktop produces 13.6px on the exact phone this app is designed for. That's backwards for an app whose own principles open with "mobile-first is literal" and "in-store use is a first-class case" — the phone is getting less legible text than the desktop nobody uses one-handed in a shop.

Colour: three authoring paths, one accidental

The tokens in src/index.css are disciplined — a single OKLCH hue variable drives every accent and semantic colour, exactly as UI_DESIGN.md §3 specifies, and the worst-case-hue sweep documented in the file's own comments is good practice. But three tokens sit outside that system as flat literals: --text/--text-h/--text-muted (hex, both themes), --code-bg (hex), and the entire --success/--success-bg/--success-border family (hex + rgba()). --focus-ring is also a flat hex, deliberately independent of the accent hue. I found no literal oklab() function anywhere in the tree — the reviewer's third mechanism most likely is this hex/rgba cluster; Chrome's computed-style inspector frequently reports alpha-composited colours in OKLab space in its picker, which would explain the label even though the source never writes oklab() by hand. Same practical problem either way: a colour not sourced from the one system.

The 184px bar

src/routes/pantry/pantry.module.css:169 — .meter { max-width: 12em; }. It reads as responsive because it's an em, not a flat px. But it sits in a 0.85rem (15.3px) text context, so 12em resolves to a fixed 183.6px regardless of the row it's in — 15% of a 1198px desktop row, nearly the full width of a 220px phone row. The unit disguised a hardcoded pixel value as a font-relative one.

Spacing that isn't a system

The six-step --space-1..6 scale (4/8/12/16/24/32) is used correctly 313 times. Against that, 95 raw pixel values leak into padding/margin/gap — clustering hardest at 5, 7, 9, 11 and 13px, which read as informal half-steps nobody named. The clearest single case: src/routes/plan/plan.module.css's per-slot action row (Cook / Reroll / Pin / Remove) uses gap: 6px between the constructive icon buttons, then isolates Remove with .iconButtonPushRight { margin-left: auto } — a real and correct technique, but the only isolation cue on the row. Nothing marks it as deliberate; it reads as whatever space the flex container happened to have left over.

02 · Proposed scales — type

Eight roles, fixed steps, one root

Fix root font-size at 18px, unconditionally — delete the 1024px media-query flip — and move every component off rem onto named, pixel-valued roles. rem is banned in src/ per CLAUDE.md; this makes the ban mechanical instead of tribal (see Enforcement). Eight roles replace the 38 raw declarations found in the audit — fewer than the six-ish "sizes that look different" a reader can actually perceive, so every one earns a name a developer can reach for on purpose.

02 · Proposed scales — spacing

Eight steps, not six — one new rung, not a rebuild

The existing --space-1..6 (4/8/12/16/24/32) is used correctly 313 times — it doesn't need replacing. It needs exactly one more rung to absorb the 5/7/9/11/13px cluster that's currently improvised, plus a named hairline for the 1–2px nudges that are legitimately not "spacing" in the layout sense.

  • hairline (2px) — icon-to-baseline nudges, the kind of offset that isn't really "space between things," it's optical correction. Not a rhythm step; don't chain two of these expecting 4px.
  • space-1 (4px) — tightest real gap: icon-to-label inside one compact control.
  • space-tight (6px) — new — absorbs the 5/6/7px cluster: gaps between peer icon buttons in an action row, chip internal padding.
  • space-2 (8px) — default small gap: list-row internal spacing, most badge padding.
  • space-3 (12px) — the 9/11/13px cluster rounds here: row padding, form-field gaps.
  • space-4 (16px) — card/panel padding, section-internal gaps.
  • space-5 / space-6 (24 / 32px) — section-to-section and page-level rhythm, unchanged.

Anything above 32px (the single 64px hit, hero spacing in the mock) is a layout decision — page-level rhythm, not a component token — and belongs to the parallel layout-layer proposal, not this one.

The root-font-size media query

Not in the table above because it isn't a value-to-value mapping — it's a rule to delete. @media (max-width: 1024px) { font-size: 16px } on :root comes out entirely. Every --fs-* role becomes a fixed pixel value that means the same thing on every screen size; where a role genuinely needs to be bigger on a wide screen (h1, h2 already do this deliberately), that's an explicit second value on the role at a named breakpoint, not a silent global multiplier.

04 · What must not change

Two things are already right

The radius vocabulary

Six values, no more, mapped to component families with no drift: this is the opposite of the type-scale problem, and the fix above adds names for the two literals (999px, 50%) without touching a single rendered pixel.

--radius-sm · 6px
--radius-md · 10px
--radius-lg · 16px
--radius-pill · 999px
--radius-circle · 50%

AAA text contrast

~7:1 body text today; every colour change proposed above was checked against its background before it went in the table, not after. Nothing here should move that number down. The one place I'm not fully certain (focus ring against a same-hue accent) is flagged, not silently accepted.

Motion

Zero non-token transition durations found anywhere in the audit — three tiers, one easing curve, fully respecting prefers-reduced-motion. Not touched by this proposal at all.

05 · The fluid-type question

Fixed steps are the honest answer here

There is no clamp() in the shipped app — the fluid-looking cluster the reviewer found is rem arithmetic against a root that silently changes. The mock (design/mock-responsive.html) does use clamp(), but only on h1 and h2 (34–58px, 24–33px) — a genuinely editorial, hero-moment use.

My call: don't adopt real clamp() anywhere in the component layer, including those two headings. Three reasons specific to this app, not a general fluid-type objection:

  1. List-first, not editorial. UI_DESIGN.md §6 already treats tables as the enhancement over lists; the same instinct applies to type. A smoothly interpolating headline earns its keep on a marketing page read at a leisurely scroll speed. Feeder's h1 is a screen label glanced at once — "Pantry", "Shopping" — where a headline that's 34px on a phone and 34px on a laptop and something unpredictable in between adds variance nobody asked for.
  2. Testability. The enforcement plan below leans on asserting exact computed font-size values in tests. A clamp() result depends on viewport width at measurement time, which makes "does this equal the token" a range check instead of an equality check — weaker, and exactly the kind of softness that let three approved designs quietly not ship.
  3. It's not solving a real problem here. The two breakpoints Feeder actually needs (phone default, ≥1024px enhancement) are already served by an explicit second value per role — h1 28→34, h2 20→22 — which is simpler to reason about than a formula and produces the exact same visual result at the two widths that matter, without inventing a third state nobody designed for.

If the owner wants a genuine hero moment later — a marketing/landing surface distinct from the in-app screens — that's a new, scoped decision for that surface, not a reason to put clamp() back into the shared type roles.

06 · How we'd know it stuck

Three approved designs never reached code. This is what would have caught them.

Each of Photos, the Plan calendar, and SegmentedControl's wrap behaviour was caught by a later human review, not by the process. A token system that only lives in a document is a fourth one waiting to happen. These checks are meant to fail loudly and cheaply — most run in Node with no browser.

  • 1
    Stylelint: no literal colour outside index.css. A declaration-property-value-disallowed-list rule bans #, rgb(, oklch(, oklab( as a color/background/border-color value in every *.module.css — only var(--*) is legal there. One file authors colour; every other file references it.
  • 2
    Stylelint: rem banned repo-wide. unit-disallowed-list: ["rem"]. Turns CLAUDE.md's "rem is a trap" from a thing an agent has to remember into a thing CI refuses to merge.
  • 3
    Stylelint: no raw px in font-size/padding/margin/gap/border-radius outside index.css. Same shape as rule 1, for size instead of colour — this is the rule that makes the 95-raw-px and 12-raw-radius findings above structurally impossible to reintroduce.
  • 4
    A computed-style contract test. A small Vitest/Testing-Library (or Playwright) spec renders ListRow, CheckRow, a badge, and a caption, reads getComputedStyle(...).fontSize, and asserts each equals one of the eight canonical --fs-* pixel values. New one-off sizes fail a test, not a code review.
  • 5
    A numeric contrast sweep in CI, not a browser. The OKLCH→sRGB relative-luminance math that caught the hue-189 and hue-156 failures in WP-15b becomes a ~50-line Node script that sweeps all 360 hues on every PR touching index.css and fails under 4.5:1 (7:1 for the AAA-committed text tokens). Runs in under a second; no Playwright needed. Turns "we tested once" into "CI tests every time."
  • 6
    ESLint: no raw pixel dimensions in src/ui/** inline styles. Same enforcement shape as the existing no-restricted-imports boundary rule in §7 — bans a literal px number inside a JSX style={{}} prop. This is what would have caught a component-level 184px-style hardcode at the authoring point, not after a reviewer measured the rendered page.
  • 7
    Mock-parity check. A short script greps design/mock-responsive.html for every custom-property name it defines and asserts each also exists in src/index.css, failing CI when the mock invents a token the app doesn't have yet. Doesn't catch every unported design (that needs the "systematic sweep" already logged in STATUS.md's Known debt), but it catches the token-layer half of exactly the pattern that burned this project three times.

Status: proposal only, on branch design-tokens. No file under src/ was touched to produce this document. A parallel agent owns the layout layer (containers, breakpoints, per-screen density); anywhere this proposal implies a layout call — the 184px meter's real width, the icon-row grouping cue, anything above 32px of spacing — it's named as a role here and left for that reconciliation, not decided unilaterally.
