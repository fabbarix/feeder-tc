Responsive system · phone · tablet · desktop

Feeder at every width, not just two

design/mock-screens.html approved phone and desktop. The owner then opened the live app on an iPad at ~1378px and found it neither — two-column recipe cards with a clipped STAPLE tag, three stacked full-width blocks above the Ingredients list, a Location filter that can't fit its own fourth option, and a seven-day week squeezed to ~90px a day. Every one of those is the same root cause: the app has one breakpoint (768px) and treats a tablet as a narrow desktop. This file adds the missing middle tier and shows all ten screens through it. It extends the approved mock — same tokens, same components — it does not replace it.

The three tiers

Breakpoints picked from what actually stops fitting, not from device names — an iPad is not a small desktop and a phone-plus is not a small tablet.

Breakpoints
Phone · 0–767px (unchanged)

One-handed thumb reach is the primary input model here — UI_DESIGN.md §1's mobile-first rule and §5's in-store shopping case both assume it. Bottom tab bar, FABs and bottom sheets are all reach-optimised; a pointer-oriented top nav has nowhere to put six links plus a workbook switcher below this width without wrapping. Nothing about this tier changes — the phone frames below are copied unchanged from the approved mock.

Tablet · 768–1439px (new)

Wide enough for a persistent top nav — brand, six links and a workbook switcher need roughly 650px+ to lay out on one line without wrapping — but not wide enough to show seven day columns, a 250–300px context rail, and a multi-column card grid all at comfortable widths simultaneously. This is exactly the band the app currently skips: every one of its 12 min-width:768px rules keeps firing, unchanged, all the way to whatever comes next, so a tablet silently inherits the desktop layout. The owner's 1378px iPad sits in the middle of this tier — comfortably clear of both edges, so the fixes below aren't tuned to one specific device width.

Desktop · 1440px+ (was ~1680px-tuned, now scales down to 1440)

The point past which a full seven-column week (7 × ~170px comfortable + 6 gaps) fits beside a capped 250–300px rail without any column dropping below a legible width. It's deliberately not 1280 — a 12.9" iPad Pro in landscape is 1366px, and a large tablet is still a touch-primary device held or propped, not a desktop with a mouse and full peripheral vision. The line is about input model and layout headroom, not raw pixels, and 1440 is comfortably past every current tablet's landscape width.

What's actually broken, precisely. Four things, all traced in the live CSS, not guessed: (1) AppShell.module.css's .mainMeasure caps content at 840px from 768px up — correct for prose, wrong for Ingredients, which inherits it because it isn't in AppShell.tsx's WIDE_ROUTES, so its list sits in an 840px column with ~270px of dead margin on either side at 1378px. (2) recipes.module.css's .tagRow sets flex-wrap:nowrap;overflow:hidden — correct on .cardMeta right above it (the "one line, never two" rule), copied by mistake onto the tag pills, which the approved mock deliberately wraps (.rtags{flex-wrap:wrap}). That's the literal "STAPLE" → "STAPLI" clip. (3) pantry.module.css's .layout splits minmax(0,2fr) minmax(220px,1fr) — a proportional third of the viewport for the rail, so it grows without bound as the viewport does, instead of a capped width. (4) SegmentedControl.module.css's .group is inline-flex with no wrap and no per-segment flex-grow — a fourth option in a narrow rail has nowhere to go but overflow or crowd. None of these four need a new component; they need the tablet-tier rules below.

Home

No layout defect reported here, but this is the screen a household opens most, so it's shown in its empty-photo state — a fresh household's normal appearance, not the exception. Tablet gets the desktop's top nav a tier early, but stays single column: the "use these first" card drops below the day cards rather than squeezing beside them at a width that would leave each too narrow.

Storage and loading, per DESIGN_PRODUCTS.md §5 — reused, not reinvented. A photo is a 512px WebP capped to a 32KB byte budget (encoder steps quality 85→35 at 512px, then downscales to 448 → 384 → 320px if it still doesn't fit, same ladder already settled for product photos), because a Google Sheets cell holds 50,000 characters and base64 inflation puts the real ceiling at ~36.6KB — a hard limit, not a preference, so there's no case for a bigger budget just because this hero renders larger on the detail page than a product thumbnail does. Photos live in a dedicated sheet rather than a column on Recipes: readAll() pulls a whole sheet, and a photo column on the Recipes sheet itself would drag all 18 images down the wire just to list recipes. Updated since this was drafted: WP-PHOTO (PR #30, merged) settled on one unified Photos sheet keyed on (ownerKind, ownerId) — it absorbed M6-A's per-entity ProductPhotos, and there is no separate RecipePhotos sheet. The reasoning below is unchanged; only the sheet count is. The grid never fetches a photo it isn't showing. Recipes render immediately from the text-only list; a card whose recipe has a photo shows Skeleton in the media box until that one photo is fetched — lazily, only once the card is on screen — then crossfades in (opacity, 220ms, the kit's own State-tier motion). A card whose recipe has no photo never issues a fetch at all. One stored resolution serves both the ~200px grid card and the larger detail hero; generating a second "thumbnail" size would mean a second sheet column for a cosmetic gain that isn't worth the contract complexity. Dependency, now resolved: this assumed the Recipes sheet carries a cheap hasPhoto signal so the list can decide skeleton-vs-placeholder without touching the photo sheet at all. WP-PHOTO (PR #30, merged) added exactly that — Recipe.hasPhoto? and Ingredient.hasPhoto?, optional and additive — so this is no longer a flagged assumption.
The tag clip's actual cause. recipes.module.css's .tagRow carries flex-wrap:nowrap;overflow:hidden — correct on .cardMeta directly above it (times must stay one line), copied onto the tag pills by mistake. This mock's .rtags has always used flex-wrap:wrap with no overflow at all; that's the one-line diff that fixes it. Tag rows must wrap or truncate a whole word, never clip mid-word — never overflow:hidden without either text-overflow:ellipsis on a genuinely single-line element, or (as here) just letting the row grow.

Why this unifies with Recipes rather than staying bespoke. Both are flat, unordered, browsable catalogues — the opposite of Pantry and Shopping, which are grouped by urgency or aisle and where row order carries real information. A page action top-right, a compact search pill, and a reflowing grid are the right shape for "browse a list of things and open one"; three stacked full-width blocks were never a deliberate pattern, they were just what was left after nobody had a mock to build to.
A real thumbnail replaces the generic glyph — and for the seeded catalogue, "no photo" IS the catalogue. The 104 seeded ingredients ship with zero photos; a household adds them one at a time as they happen to matter. So Minced beef (a photo), Rice (still loading — the row rendered immediately, the one visible photo is being fetched lazily) and everything else (the calm neutral square) are all in the row above, and the "everything else" state is the one that actually describes day one, not an edge case to design around later. 52px keeps a fetch-per-visible-row scheme affordable at catalogue scale — Pantry and the pantry-item page reuse the exact same .ithumb at the same size, since they're the same entity (see below); Shopping deliberately does not.

Where else does an ingredient photo earn its place? Argued case by case, not applied by reflex. Yes — Pantry list and the pantry-item page. Same entity as Ingredients (a lot of Rice IS Rice), so the identical 52px .ithumb belongs on both, for recognition scanning a long pantry list the same way it helps scanning the catalogue. Yes, small — a recipe's ingredient lines. The 40px row in .ilist is denser than Pantry's, so a thumbnail there is smaller still (36px) and optional — it earns its place only where the list is genuinely long enough that names alone blur together, which most recipes' 4-6 lines are not; treat it as a nice-to-have, not designed further here. No — the shopping list. UI_DESIGN.md §1 invariant 5 is explicit: used one-handed, in a supermarket aisle, possibly on a bad connection. The row's job is one thing — a big tap target that toggles checked — and its trailing space already carries the quantity. A thumbnail competing with the tick and the quantity for a touch target that's supposed to be unmissable is noise, not recognition help; you're standing in front of the tomatoes, you don't need a photo of one to identify it.

Base 4 · surplus becomes a leftover lot when cooked.

No photo, no inset — the page you're reading today, not a placeholder. Different rule from the grid's, argued from what each screen actually needs: a card grid has neighbours to line up against, so every card claims the same 80px square whether or not a photo fills it. A single recipe page has no row to stay level with — with no photo, this screen has no inset at all; Chili's page would simply start at the tag row, exactly as it does today. An empty glyph panel would offer a reader nothing — they're looking at a recipe, not editing one — so the honest default for most recipes (no photo yet) is that the photo slot doesn't exist on this page until one does. The "add a photo" affordance belongs on the editor, next.
Steps: a short line always, an image and a timer only where they earn it, detail behind a fold. Step 1 has no image (the default — most steps never get one, same reasoning as everywhere else in this package); step 2 has a duration but no image, so it's just a badge plus a Start timer button; step 3 has all three: a 240px .rstepimg (a clarifying "what it should look like here," not a feature photo — small is honest at this budget), a running timer, and a <details> disclosure for the kind of explanation that would otherwise force every reader to scroll past three sentences to find step 4. Native <details>/<summary>, not a custom toggle: free keyboard and screen-reader behaviour, and it degrades to just-shown if CSS fails to load. The running timer on the phone frame is deliberately the boldest thing on the page — full --accent, 36px tabular digits, 44px pause/cancel targets — because this is used with flour on your hands, glancing from across the counter, and a quiet resting-state badge would be exactly wrong for that moment. Step images load the same lazy-per-visible-item way as everything else in this package: a 6-step recipe with images is 6 more fetches, each behind its own Skeleton, triggered as the step scrolls into view — not fetched with the recipe.

Every filled slot above now has a Remove icon, including past ones — previously there was no way to remove a slot at all once it existed.
